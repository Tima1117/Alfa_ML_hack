# Инфраструктура: запуск и сборка

Основа: ThrPHP/Alfa_ML_hack_D, `agent-v1` (1f1af57), плюс документация из 97e0dd0.
Исходники `agent/` и `ml_core/` не изменены инфраструктурой.

## Как устроен ZIP

В корне ровно три файла: `solution.py`, `bundle_sources.py`, `requirements.txt`.
Первый запускает наблюдатель. Второй содержит обычные строки исходного кода проекта
и их SHA-256, без сжатия/шифрования и сторонних библиотек. При старте исходники
восстанавливаются в уникальную подпапку `<task dir>/agent_work/runtime_*`.
Так сохраняются импорты пакетов, `python -m agent._worker` и файл песочницы рядом с модулем.
Правило о копировании только корневых файлов выполнено, файлы не загружаются из сети.
Данные, инструкции для ассистентов, ключи, .venv и файлы модели в ZIP не включаются.

## Запуск на платформе

```sh
python3 solution.py /path/to/task.md
```

Подключение Qwen: `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL` из среды платформы.
Ключ в файлы не записывать. При отсутствии ключа агент продолжает без LLM.
Выход: `submission.csv` рядом с `task.md`, независимо от текущего рабочего каталога.
Нужен Python 3.12 и предустановленные библиотеки организаторов; из решения ничего не устанавливается.

## Что ограничивается

- Отсчет с начала `solution.py`, включая восстановление кода и импорты.
- По умолчанию агент получает 2 ч 50 мин; наблюдатель останавливает работу к 2 ч 59 мин 30 с.
- Не больше 8 потоков на обучение, дополнительно задаются переменные OpenMP/BLAS.
  На Linux дочерним процессам ограничивается набор доступных CPU.
- Наблюдатель раз в 0.2 с считает суммарную RSS собственных процессов; при >28 GiB останавливает их.
  RSS может дважды учитывать общую память. Это консервативный мониторинг, не жесткая квота памяти ОС:
  быстрый скачок между замерами возможен. Внешнюю границу 32 GB обеспечивает контейнер платформы.
- Имеющиеся таймауты отдельных экспериментов сохраняются (обычно максимум 1800 с).
- При остановке завершаются и отдельные сессии воркеров. В дополнение к дереву psutil
  Python-процессы регистрируют созданные подпроцессы; это работает при ограничениях macOS.
- Окончательный CSV проверяется независимо: столбцы, число строк, порядок и уникальность ID,
  допустимые классы или конечные числа. При корректном сохраненном ответе выход 0,
  даже если агент завершился с ошибкой. Ошибка видна в отчете, а не скрывается.

Код признаков от LLM остается частью агента. Фильтр кода и отдельный процесс не являются
защитной песочницей ОС. Для реальных запусков используйте выделенный контейнер без личных файлов.

## Настройки для локальной проверки

| Переменная | По умолчанию | Значение |
|---|---|---|
| `INFRA_TOTAL_SECONDS` | 10800 | Общий бюджет, 10..10800 с |
| `INFRA_SAFETY_SECONDS` | 600 (меньше при коротком бюджете) | Резерв до конца общего бюджета |
| `INFRA_MEMORY_GB` | 28 | Порог суммарной RSS в GiB, можно уменьшить |
| `AGENT_N_JOBS` | min(8, CPU) | Потоки, положительное число до доступного максимума |
| `AGENT_DISABLE_LLM` | не задана | `1` для бесплатного прогона |

Остальные настройки — `docs/AGENT_CONTRACT.md`. При ограниченной памяти ноутбука задавайте
`INFRA_MEMORY_GB` явно ниже доступной памяти; производственный стандарт 28 предназначен для контейнера 32 GB.

## Как пересобрать после изменений команды

Из корня репозитория:

```sh
python3 scripts/build_submission.py /path/to/alfa_solution.zip
```

Рядом создается manifest JSON: версия основы, контрольная сумма ZIP и каждого исходника.
Повторная сборка одинакового кода дает одинаковые байты ZIP. Наличие плоских файлов проверяется тестами.
Нельзя отправлять весь репозиторий вместо собранного архива.

## Как проверить именно архив

В окружении Python 3.12 с библиотеками из `infra/requirements.runtime.txt`:

```sh
python3 scripts/verify_submission.py /path/to/alfa_solution.zip "Base/Datasets/Регрессия/task.md" /tmp/check-regression --budget-s 300 --jobs 2
python3 scripts/verify_submission.py /path/to/alfa_solution.zip "Base/Datasets/Многоклассовая классификация/task.md" /tmp/check-multiclass --budget-s 300 --jobs 2
python3 -m pytest tests/ -q
```

Каталоги `/tmp/check-*` должны быть новыми. Проверяющий скрипт удаляет настройки API из среды
дочернего процесса и отключает LLM; деньги не расходуются. На macOS моделям LightGBM/XGBoost
нужна локальная OpenMP; на Linux пакет libgomp1 предусмотрен Dockerfile.

Дополнительная Linux-проверка (Docker нужен на компьютере):

```sh
docker build -f infra/Dockerfile -t alfa-infra-check .
# Распаковать alfa_solution.zip в /absolute/package, данные задачи разместить в /absolute/task.
docker run --rm --network none --cpus 8 --memory 32g \
  -e AGENT_DISABLE_LLM=1 -e INFRA_TOTAL_SECONDS=300 \
  -v /absolute/package:/solution:ro -v /absolute/task:/task \
  alfa-infra-check /task/task.md
```

Контейнер использует закрепленные версии реально импортируемых библиотек; это не полный
образ платформы. Автоматический антивирус и защита от намеренно враждебного кода не реализуются.

## Где смотреть результат и ошибки

- `submission.csv` — предсказания для платформы.
- `agent_work/process.log` — весь вывод агента и библиотек.
- `agent_work/infra_report.json` — причина завершения, код агента, пиковая RSS, результат проверки CSV.
- `agent_work/report.md` и `report.json` — исследовательский отчет агента, если он успел сформироваться.
- `agent_work/experiments/experiments.jsonl` — эксперименты.

Короткий успешный прогон не доказывает работу 3 часа, качество на hidden test или доступность API.
Долгий прогон и запросы к настоящей LLM проверяются отдельно с учетом бюджета команды.

## Реальный инцидент: первый сабмит получил 0 баллов по обеим задачам (21 октября 2026)

Организаторы: «код запустился, но после завершения дочернего процесса ваш скрипт попытался
прочитать отсутствующий submission.csv, выполнение прервалось». То есть `submission.csv` не
появился вообще — не плохое качество, а полное отсутствие файла.

Причина — `child_main()` вызывал `os.sched_setaffinity(...)` **без try/except**, до вызова
`run_research()`. А `run_research()` — единственное место, где пишется аварийный `submission.csv`
(первым делом внутри `prepare()`). Платформа организаторов, судя по всему, запускает контейнеры
участников в более строгой песочнице, чем обычный Docker (вероятно, ограничение через seccomp —
нормально для платформы, исполняющей произвольный код десятков команд). `hasattr(os, "sched_getaffinity")`
возвращает `True` даже там, но сам системный вызов может быть запрещён ядром и кинуть `PermissionError`
во время исполнения — именно это и произошло: падение случилось раньше, чем `run_research()` успел
написать хоть что-то.

Локально воспроизвести точное ограничение их песочницы не удалось (обычный Docker и
`--cap-drop=ALL` этот syscall не блокируют) — но механизм подтверждён юнит-тестом
(`tests/test_infrastructure.py::test_child_main_still_calls_run_research_if_cpu_pinning_is_denied`):
с замоканным `os.sched_setaffinity`, кидающим `PermissionError`, тест падал той же ошибкой до
фикса и проходит после.

**Фикс**: обе операции в `child_main()` до вызова `run_research()` (попытка закрепить CPU и
предварительная запись `infra_task_spec.json`) теперь обёрнуты в `try/except Exception: pass` —
они необязательны (`--cpus` на уровне контейнера и `AGENT_N_JOBS` уже ограничивают реальное
использование CPU без явного pinning), и ничего до `run_research()` не должно иметь возможности
помешать её вызвать.

**Урок для любого будущего `child_main()`-подобного кода**: единственная гарантия
непустого `submission.csv` — это то, что происходит *внутри* `run_research()`. Всё, что
исполняется раньше неё, обязано быть защищено try/except, даже самое безобидное на вид.

## Проверка уточненного контракта (21 октября 2026)

Присланный командой CONTRACTS.md подтверждает фильтрацию файлов при загрузке.
Наш ZIP уже соответствует этому правилу; исходники в нем лежат в корневом `.py`,
а рабочие папки создаются только после старта. Сборка не требует переписывания
импортов, поскольку имена восстановленных пакетов сохраняются.

Для проверки буквального сценария платформы добавлен режим:

```sh
python3 scripts/verify_submission.py /path/to/alfa_solution.zip /path/to/task.md /tmp/new-platform-check --budget-s 300 --jobs 2 --platform-copy
```

Режим копирует только корневые `.py` и `requirements.txt` прямо к данным задачи,
отбрасывает вложенные файлы и запускает `python solution.py task.md` из этой папки.
Результаты ревизии — `docs/CONTRACT_REVIEW.md`.
