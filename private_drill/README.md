# Synthetic "private-like" task — a drill, not a real competition dataset

Generated locally (not from the organizers) to stress-test the pipeline against
something structurally unlike the two known public tasks, since the brief warns
private-task metrics "may differ". Same guaranteed file shapes
(`train.csv`/`test.csv`/`data_dictionary.csv`/`sample_submission.csv`/`task.md`),
different domain (loan-default prediction, not buildings or network traffic),
and deliberately probes known risk areas:

- **Metric stated as ROC-AUC** in `task.md` — a probability-scored metric, unlike
  both real public tasks (RMSE, Macro F1), which only ever need hard predictions.
- **Severe class imbalance** (~5% positive) — this is what actually surfaced the
  finding below; a balanced synthetic target wouldn't have.
- A disguised time column (`application_batch`: train has 1-6, test is only 7) and
  an unseen-at-train-time category (`region_code` has `R90`/`R91` only in test) —
  the same shape of risk as `Year_Factor`/`state` in the real public tasks, just
  with different names, to confirm nothing is hardcoded to those specific columns.

## What this drill actually found

**#1 — no `predict_proba`.** Before the first fix in this commit range,
`ml_core` always called `model.predict()` for classification, never
`model.predict_proba()`. Under this fixture's imbalance, that collapsed to
predicting the majority class for every single row — a valid *label*, but a
submission with **zero discriminative power** for ROC-AUC (≈0.5, random),
regardless of how good the underlying model actually was. Confirmed by the
submission literally being 100% "No" before the fix, and a real spread of
1500 distinct probabilities after it. See docs/CONTRACTS.md's
"Probability-scored metrics" section for the fix.

**#2 — single-fold `time_split` overfits local search.** The target is
generated by a known logistic formula (`train.csv`/`test.csv` have no hidden
truth file, but the generator script — not committed, seed `1234` — is fully
reproducible), which makes it possible to compute the true Bayes-optimal
ceiling for this exact data and score the actual submission against the real
hidden labels instead of only trusting the model's own validation number:

| | ROC-AUC |
|---|---|
| Bayes-optimal ceiling (best any model could ever achieve on this data — the generator injects irreducible noise) | 0.667 |
| Single-fold `time_split` validation estimate, after ~90 LLM + local-search experiments | 0.725 (optimistic) |
| **Actual score against the true hidden test labels** | **0.653** |
| Same submission's *own* validation estimate once `time_split` runs 3 walk-forward folds instead of 1 | **0.594 ± 0.08** (now closer to truth, erring cautious rather than optimistic) |

With only one held-out period, ~90 rounds of local search had nothing to
overfit *to* except that single fold's own noise — the model's reported
0.725 was never real. `ml_core.validation`'s `time_split` now walks forward
over multiple periods by default (`agent/understand.py` picks
`min(3, n_unique_periods - 2)` folds) specifically because of this finding;
see docs/CONTRACTS.md for the fix itself.

## Re-running it

```bash
python scripts/run_agent_local.py private_drill/task.md --budget-s 180 --no-llm
```

Drop `--no-llm` (and set `OPENAI_API_KEY`/`OPENAI_MODEL`/`OPENAI_BASE_URL`) to also
exercise the LLM's own hypothesis generation against a metric/domain it hasn't
seen tuned prompts for. Output goes to `runs/agent/private_drill/` by default —
gitignored, regenerate rather than relying on a stale copy.
